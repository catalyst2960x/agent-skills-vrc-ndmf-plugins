# Diagnosing a Failing Case

A failing case has four possible homes: the fixture, the
case itself, the product, or a dependency. The triage order
removes the cheap ambiguities first.

## 1. Run the base cases

Run the base verification cases. A failure there means the
fixture or the environment changed — a dependency updated,
the minimal avatar no longer builds — and every product
case failing at once is the signature. Fix the base before
reading any product failure.

One base signature names itself: assertions pass and the
runner still reports the test failed, with the failure in
teardown — "Destroying assets is not permitted". The base
destroyed a tracked asset object (a controller, a clip)
without the asset flag. The fix is in the base's teardown,
and no product case reading follows from it.

## 2. Run the failing case alone

A case that passes alone and fails in the suite is order
dependence: residue from an earlier test, most often an
untracked object or a temp asset teardown deleted. A case
that fails alone is deterministic; keep it alone for the
rest of the triage.

## 3. Bisect pass against pipeline

Run the same fixture at the direct context and through the
full pipeline — the agreement case is the tool. Agreement
with a product failure puts the defect in the pass.
Divergence puts it in ordering or in another system's
effect on the pass's input, and the generated output is
read at both layers to find where it changes. When another
system's layers appear inside a difference the case is
measuring, suspect that system's placement-dependent
insertion first — an insertion rule that fires in only one
of the compared builds puts its layers in the difference
without the plugin contributing them (Test Infrastructure,
Framework defaults in fixtures).

## 4. Read the report before the output

A build that reported NonFatal or Information for the
fixture's configuration generated by a different path than
the case assumed. The captured report states which input
the pass rejected; an output assertion failing beside an
unexpected report is a fixture or configuration defect
until the report is explained.

## 5. Separate product from dependency

When the pass and the pipeline agree and the report is as
designed, compare against the dependency's own behaviour:
the framework's version in the project against the skill's
anchors, and the framework's own test expectations for the
mechanism in question. A behaviour that changed across a
dependency update is recorded as a dependency change, with
the version, before the product is changed to match it.

## 6. Counts come from the fixture, and a fix is confirmed running

A count assertion — conditions on a transition, parameters
declared, reports captured — takes its expected value from
the fixture's actual inputs, enumerated: the elements of
the chain the fixture builds, the components it carries,
the entries it defines. When a count disagrees, the
enumeration is checked against the expectation before the
product is suspected; a chain of two elements produces two
conditions however the case was first written.

After correcting a case, confirm the corrected code is what
ran — a changed diagnostic string or a shifted line number
in the failure — before judging the new result. An
environment that can run stale compiled code makes an
unchanged failure after a fix ambiguous between "the fix is
wrong" and "the fix never ran".

## 7. Record the finding with the case

The triage outcome — which home the failure had — is
recorded with the case or the defect record it produced, so
the next failure of the same shape starts from the finding,
not from the beginning.
